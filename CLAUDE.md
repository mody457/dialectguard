# CLAUDE.md

## Project Overview

DialectGuard is a production-grade Gulf Arabic dialect classification API.
It classifies Arabic text into one of six Gulf dialects: Oman (OM), Saudi
Arabia (SA), Kuwait (KW), Qatar (QA), Bahrain (BH), and United Arab
Emirates (AE). The core use case is content routing and moderation for
Gulf-region Arabic text (e.g., customer service routing, comment
filtering, model routing by dialect).

## Architecture

- **Serving**: FastAPI (async, Pydantic schemas for request/response validation)
- **Model**: Fine-tuned MARBERTv2 (UBC-NLP/MARBERTv2), sequence classification head, 6 labels
- **Experiment tracking**: MLflow
- **Containerization**: Docker, multi-stage build
- **CI/CD**: GitHub Actions (lint -> test -> eval harness -> docker build -> push)
- **Monitoring**: Evidently (data drift detection, post-deployment quality reports)
- **Data/model versioning**: DVC

## Trained Model

- Location: `models/dialectguard_model/` (contains `model.safetensors` and `config.json`)
- Base model: UBC-NLP/MARBERTv2
- Fine-tuned on cleaned QADI Gulf-subset data (mentions/hashtags/URLs stripped
  to prevent account-identity leakage — this was a critical bug found and
  fixed during training; do not reintroduce raw @mentions or #hashtags as
  model input features)
- Label mapping (index -> country code):
  `0: OM, 1: SA, 2: KW, 3: QA, 4: BH, 5: AE`
- Official test set performance (macro F1): 61.8%
- Baseline (TF-IDF + Logistic Regression) for comparison: 44.6% macro F1

## Writing Style (README, docstrings, comments, commit messages, PR descriptions)

All written text this project produces must read like it was written by a
careful human engineer, not generated by an AI.

- No em dashes. Use periods, commas, or parentheses instead.
- No AI-sounding filler phrases ("It's worth noting that", "In today's
  fast-paced world", "This powerful tool", "Let's dive in").
- No excessive enthusiasm, no exclamation marks in technical docs.
- Write short, direct sentences. Say the thing plainly.
- Avoid rigid three-part list patterns repeated everywhere (e.g., every
  section having exactly 3 bullet points with the same rhythm). Vary
  structure the way a human naturally would.
- Avoid restating the obvious before saying something ("To summarize, in
  conclusion, overall"). Just state the point.
- Technical docs should sound like internal engineering notes: precise,
  a little terse, no marketing tone.

## Code Standards

- All code, comments, docstrings, variable/function names, commit messages,
  and technical documentation (README, API docs, inline comments) MUST be
  in English. This is a production codebase and portfolio piece — no
  exceptions.
- Follow PEP 8 for Python. Use type hints on all function signatures.
- Use Pydantic models for all FastAPI request/response schemas — no raw
  dicts in endpoint signatures.
- Prefer explicit over implicit. No magic numbers — use named constants
  (e.g., `MAX_TEXT_LENGTH = 128`, not a bare `128` scattered in code).
- Every new module/function that does non-trivial work needs a docstring
  explaining *why*, not just *what*.
- Pin exact dependency versions in `requirements.txt` (use `==`, not `>=`),
  to keep the environment reproducible across dev, CI, and Docker.

## API Design Standards

- Version the API from day one: all routes under `/api/v1/`.
- Every endpoint returns a consistent error shape on failure (status code,
  error code, human-readable message). Do not let raw stack traces leak
  into API responses.
- Validate input length and encoding before running inference. Reject
  empty strings, non-Arabic-dominant text, and text over the model's
  max token length with a clear 4xx error, not a silent bad prediction.
- Return prediction confidence alongside the predicted label. Do not
  return a bare label with no probability — downstream systems need to
  know how uncertain the model is.
- Include a `/health` endpoint (checks model is loaded, not just that
  the process is alive) and a `/version` endpoint (model version, API
  version, git commit hash).

## Security

- Never hardcode secrets, API keys, or credentials in source code.
  Use environment variables, loaded via `.env` locally (gitignored) and
  injected via the deployment environment in production.
- Sanitize and cap input text length before it reaches the tokenizer to
  prevent resource-exhaustion abuse.
- Add basic rate limiting on the prediction endpoint before considering
  it production-ready.

## Logging

- Use structured logging (JSON lines), not bare `print()` statements.
- Log every prediction request with: timestamp, input length, predicted
  label, confidence, latency. Do not log full raw input text by default
  (privacy) unless a debug flag is explicitly set.
- Log level should be configurable via environment variable, defaulting
  to INFO in production and DEBUG in local development.

## Testing

- Every new feature or endpoint requires corresponding unit tests before
  being considered complete.
- Use pytest as the testing framework.
- The eval harness (model accuracy on held-out Gulf dialect test data)
  must pass a minimum macro F1 threshold before any Docker build in CI.
- Include at least one test that sends known-dialect example text through
  the full API path (not just the model function directly) and checks
  the response shape and status code, not just the predicted label.

## Text Preprocessing Rule (Critical)

Any text preprocessing pipeline used at inference time MUST match the
preprocessing used during training exactly:
1. Strip @mentions
2. Strip #hashtags
3. Strip URLs
4. Normalize whitespace

Failing to replicate this preprocessing at inference time will cause a
train/serve skew and degrade real-world accuracy below the documented 61.8%.

## Known Limitations (must be reflected in API docs / README)

- Model trained exclusively on Twitter/X data; performance on other text
  sources (WhatsApp, reviews, forums) is unverified.
- Possible residual user-level leakage in train/test split (no explicit
  user_id in source dataset; only exact-text-duplicate leakage was ruled out).
- Class imbalance exists in training data (Kuwait overrepresented relative
  to Oman); per-country performance varies (see confusion matrix in docs/).
- 61.8% macro F1 means roughly one in three predictions is wrong. This is
  not production-ready for high-stakes routing decisions without a human
  review step or a confidence threshold gate.

## Git Workflow

- Feature branches only; no direct commits to `main`.
- Commit messages: imperative mood, present tense (e.g., "Add dialect
  prediction endpoint", not "Added" or "Adding").
- Do not commit model weights (`*.safetensors`) directly to git — use
  DVC or Git LFS.
- Keep commits scoped to one logical change. Do not mix a dependency
  bump with a feature change in the same commit.

## Definition of Done (for any new feature)

A feature is not complete until all of the following are true:
1. Code is written and follows the standards above.
2. Unit tests exist and pass.
3. The eval harness still passes its F1 threshold (if the change touches
   the model or preprocessing pipeline).
4. Documentation (README or inline docstrings) is updated to reflect the
   change.
5. No secrets, debug prints, or commented-out dead code are left behind.

## What NOT to Do

- Do not retrain or fine-tune the model without explicit instruction —
  training is expensive and was already completed with a validated,
  documented result.
- Do not silently change the label order/mapping (0-5 -> country codes) —
  this would break compatibility with the already-evaluated model.
- Do not add new dependencies without checking `requirements.txt` first
  to avoid version conflicts.
- Do not claim or imply higher model accuracy than 61.8% macro F1 in any
  documentation, docstring, or API description.
- Do not remove or weaken the text preprocessing step to "simplify" the
  code — it exists specifically to prevent train/serve skew.
